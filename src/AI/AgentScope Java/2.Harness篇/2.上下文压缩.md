## 概述

大模型每次"思考"能读的文字量是**有限**的（token 预算）。对话越聊越长，迟早会撑爆。所谓"上下文压缩"，就是**在尽量不丢关键信息的前提下，把对话历史瘦身**，让它继续跑得下去。

**一个类比**：把对话想象成一张越写越长的草稿纸，桌面（token 预算）就这么大。压缩不是随便撕，而是有几种不同的"收纳办法"。

## 压缩策略

| 策略           | 治什么病                                       | 什么时候动手         |
| :------------- | :--------------------------------------------- | :------------------- |
| 对话摘要压缩   | 聊得**太深**（消息条数 / 累计字数太多）        | 每次模型回答前       |
| 大工具结果卸载 | 单条结果**太宽**（某一次工具返回的内容特别大） | 工具执行后           |
| 上下文溢出兜底 | 实在**撑爆了**（模型直接报错）                 | 出错时               |
| 预压缩参数截断 | 工具**入参**太大但事后没人看                   | 摘要之前的轻量预处理 |

### 对话摘要压缩

**做法**：把对话**前段**让 LLM 总结成一段结构化摘要，**结尾最近 N 条保留原文**，然后用 `[摘要] + [最近几条原文]` 替换掉原来一大坨历史

```java
HarnessAgent.builder()
    .compaction(CompactionConfig.builder()
        .triggerMessages(30)     // 30 条触发
        .keepMessages(10)        // 压缩后保留最近 10 条原文
        .build())
    .build();
```

### 大工具结果卸载

**和对话摘要压缩是两码事**：对话摘要压缩管的是消息太多，大工具结果卸载管的是**某一条工具返回的内容太大**（默认超过约 8 万字符 ≈ 2 万 token）。

**做法**：把全文写到磁盘某个目录，上下文里**只留开头结尾各约 2K 字符 + 一个文件路径提示**。Agent 真想看全文，就自己去 `内部工具`。

**注意排除名单**：`内部工具`、`write_file` 这类工具默认不处理（它们要么自带分页、要么返回值本来就小）。但 **Shell 命令的 `execute` 默认不豁免**，因为命令输出可能巨大。

```java
HarnessAgent.builder()
    .toolResultEviction(ToolResultEvictionConfig.defaults())
    .build();
```

### 上下文溢出兜底

如果模型直接报 `context_length_exceeded` 这类错，系统会**强制做一次最狠的压缩**，然后**自动重试一次**。

**前提**：你必须事先开了 `.compaction(...)`。开了它，这条兜底就自动生效，无需额外配置；没开就直接把错误抛回上层。

### **预压缩参数截断**

在做 LLM 摘要**之前**，先不花模型、纯字符串层面把大入参截短。典型对象是 `write_file`、`edit_file` 这种——**写进去的内容很大，但事后没人会回看**。很多场景光靠这一步就能大幅减少"触发摘要"的次数，几乎不花成本。

```java
CompactionConfig.builder()
    .triggerMessages(80)
    .truncateArgs(CompactionConfig.TruncateArgsConfig.builder()
        .maxArgLength(2000)		// 入参超 2000 就截断
        .truncationText("... [truncated] ...")
        .build())
    .build();
```

## 与长期记忆区分

很多人担心"压缩 = 丢信息"。其实有两个开关（默认都开）来兜底：

- **`flushBeforeCompact`（摘要前先把事实写进长期记忆）**：摘要丢掉前缀消息前，先把里面的事实增量写进 `MEMORY.md`。之后 Agent 还能用 `memory_search` 查回来。
- **`offloadBeforeCompact`（摘要前把原始消息存成永不压缩的日志）**：原文存进 `*.log.jsonl`，供 `session_search` 检索。

## 与 AgentState 区分

压缩**只处理对话消息列表**。下面这些活在 `AgentState` 的其他字段里，**完全不受影响**：

- Plan Mode 的计划状态
- 子 Agent 的后台任务（存在独立文件里，靠 system reminder 反向注入，不进对话流）
- `todo_write` 任务清单
- 权限规则

所以可以放心开 `.compaction(...)`，不用担心丢掉计划或未跑完的后台任务。

## 整体逻辑

```java
对话变长
  ├─ 消息太多      → ① 摘要压缩（聊天前）
  ├─ 单条结果太大  → ② 卸载到磁盘（工具执行后）
  ├─ 入参太大      → ④ 提前截断（零成本）
  └─ 真爆发了      → ③ 兜底：极限压缩 + 自动重试

压缩前：先把事实存进长期记忆 + 原文存日志（防丢）
压缩范围：只管对话消息，plan/后台任务/权限都不碰
事后补救：Agent 可用 session_* / memory_* 工具找回原文
```
