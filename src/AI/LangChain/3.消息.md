## 前言

本篇记录 LangChain 1.x **消息（Messages）** 的完整用法

官方文档：[LangChain Messages](https://docs.langchain.com/oss/python/langchain/messages)

消息是模型交互的基本单位。A01 讲的是「怎么把模型接进来」，
A02 讲的是「接进来之后能怎么用」，
本篇讲的是**模型与外界交换信息的载体本身**——一条消息由什么组成、
有哪些类型、内容怎么组织、怎么持久化。

仍然使用阿里云百炼（DashScope）平台的 **deepseek-v4-pro-0813** 模型，
通过 OpenAI 兼容模式接入，多模态示例改用 **qwen3-vl-plus**。
示例代码见仓库中的 `A03-langchain-message`。

### 核心概念

| 概念 | 说明 |
| --- | --- |
| `SystemMessage` | 系统指令，设定模型的角色与行为约束 |
| `HumanMessage` | 用户输入，可携带 `name` / `id` 元数据 |
| `AIMessage` | 模型响应，带工具调用、用量、原始响应等信息 |
| `ToolMessage` | 工具执行结果，回填给模型继续推理 |
| `content` | 消息的原始负载，字符串或字典列表 |
| `content_blocks` | `content` 的标准化视图，跨 provider 通用 |
| `AIMessageChunk` | 流式场景下的消息分片，可以用加号累加 |
| `dumpd` / `load` | 消息的序列化与反序列化 |

## 消息组成部分

每条消息都由三部分组成：

* **角色（Role）**：这条消息是谁说的，决定了模型怎么理解它
* **内容（Content）**：真正传给模型的负载
* **元数据（Metadata）**：响应信息、消息 ID、token 用量等

```python
from langchain.messages import HumanMessage

message = HumanMessage(content="你好", name="alice", id="msg_123")
message.type      # 'human'，角色
message.content   # '你好'，内容
message.name      # 'alice'，元数据
message.id        # 'msg_123'，元数据
```

> [!NOTE]
> LangChain 1.x 提供了一套**跨 provider 通用**的标准消息类型，
> 不管底层是 OpenAI、Anthropic 还是百炼，用法完全一致。

## 基础用法

### 三种输入形式

`invoke` 接受三种输入。三者最终都会被规整成消息序列发给模型，
区别在于写起来更简洁还是更明确，以及能表达多少东西：

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage

# 1. 文本提示：字符串会被自动包装成一条 HumanMessage
response = model.invoke("写一首关于春天的俳句")

# 2. 消息提示：类型明确，支持多模态
response = model.invoke(
    [
        SystemMessage("你是一位诗歌专家"),
        HumanMessage("写一首关于春天的俳句"),
        AIMessage("樱花盛开……"),
    ]
)

# 3. 字典格式：OpenAI Chat Completions 的原生结构，便于迁移
response = model.invoke(
    [
        {"role": "system", "content": "你是一位诗歌专家"},
        {"role": "user", "content": "写一首关于春天的俳句"},
        {"role": "assistant", "content": "樱花盛开……"},
    ]
)
```

怎么选：

| 形式 | 适用场景 |
| --- | --- |
| 文本提示 | 单次独立请求、不需要历史、追求最少的代码 |
| 消息提示 | 多轮对话、多模态内容、含系统指令 |
| 字典格式 | 从 OpenAI 生态迁移，或需要在代码里拼装请求体 |

### 从哪导入消息类

`langchain.messages` 是 LangChain 1.x 的推荐入口：

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
```

它只重新导出了常用类型。需要 `ChatMessage`、`FunctionMessage`、
`BaseMessage` 这些时，从 `langchain_core.messages` 导入。

## 四种消息类型

### SystemMessage

系统消息是模型行为的「总开关」，用来设定角色、语气和约束。
它是提示词工程的主要载体。

```python
from langchain.messages import HumanMessage, SystemMessage

system_msg = SystemMessage("你是一位乐于助人的中文助手。")

messages = [
    system_msg,
    HumanMessage("如何用 FastAPI 写一个健康检查接口？"),
]
response = model.invoke(messages)
```

想要更细致的行为约束，可以写多行：

```python
system_msg = SystemMessage(
    "你是一位资深 Python 开发者，精通 Web 框架。\n"
    "回答要求：\n"
    "1. 总是给出可运行的代码示例。\n"
    "2. 先给结论，再解释原因。\n"
    "3. 表达简洁，但覆盖关键细节。"
)
```

### HumanMessage

用户输入。除了文本，还能携带多模态内容和元数据：

```python
human_msg = HumanMessage(
    content="你好",
    name="alice",  # 可选：标识不同用户
    id="msg_123",  # 可选：唯一标识，便于追踪
)
```

> [!NOTE]
> `name` 字段的行为因 provider 而异——有的用它标识用户，有的直接忽略。
> 具体看对应 provider 的参考文档。

> [!WARNING]
> **本地构造的消息默认没有 id。**
> `HumanMessage("你好").id` 是 `None`；
> 只有模型返回的 `AIMessage` 才会被自动补上
> `lc_run--<uuid>-0` 形式的 id。provider 自己的请求 id
> 在 `response_metadata["id"]` 里：
>
> ```python
> response.id                            # 'lc_run--01a1b420-adee-7776-8439-f2e8f193ab66-0'
> response.response_metadata["id"]       # 'chatcmpl-00f1977f-6c83-9204-ae77-37246f263cb8'
> ```

### AIMessage

模型返回的对象。它带的元数据比输入消息丰富得多：

```python
response = model.invoke("用两句话解释 LangChain 的核心价值。")

response.text             # 正文，纯字符串
response.content          # 原始负载
response.content_blocks   # 标准化内容块列表
response.tool_calls       # 工具调用请求，没有时是空列表
response.id               # LangChain 自动生成的唯一标识
response.usage_metadata   # token 用量
response.response_metadata  # provider 的原始响应信息
```

`response_metadata` 里是 provider 塞进来的原始字段，
各家不太一样，但几个通用的很实用：

```python
{
    "model_provider": "openai",
    "model_name": "deepseek-v4-pro-0813",
    "id": "chatcmpl-00f1977f-...",
    "finish_reason": "stop",
    "token_usage": {...},
}
```

#### 工具调用

绑定工具后，模型发起的调用请求挂在 `tool_calls` 上：

```python
def get_weather(location: str) -> str:
    """Get the weather at a location."""
    ...


model_with_tools = model.bind_tools([get_weather])
response = model_with_tools.invoke("What's the weather in Paris?")

for tool_call in response.tool_calls:
    print(tool_call["name"], tool_call["args"], tool_call["id"])
```

#### token 用量

```python
response.usage_metadata
# {
#     'input_tokens': 93,
#     'output_tokens': 223,
#     'total_tokens': 316,
#     'input_token_details': {'cache_read': 0},
#     'output_token_details': {'reasoning': 153},
# }
```

> [!TIP]
> `reasoning` 是深度思考消耗的 token。百炼上 `deepseek-v4-pro` 默认开启思考，
> 这个数字会占掉 `max_tokens` 预算的一部分（详见 A02）。

#### 流式分片

流式场景下拿到的是 `AIMessageChunk`，用加号可以累加成完整消息：

```python
chunks = []
full_message = None
for chunk in model.stream("Hi"):
    chunks.append(chunk)
    print(chunk.text)
    full_message = chunk if full_message is None else full_message + chunk
```

> [!WARNING]
> **流式分片默认不带 token 用量。**
> `invoke` 的结果有 `usage_metadata`，但 `stream` 的分片是 `None`。
> 需要统计流式用量，得显式传 `stream_usage=True`：
>
> ```python
> for chunk in model.stream("你好", stream_usage=True):
>     ...
> ```

### ToolMessage

工具执行完，结果要用 `ToolMessage` 包一层回填给模型。
它的 `tool_call_id` 必须和 `AIMessage.tool_calls` 里的 id 对上，
模型才知道这个结果是给哪次调用的。

```python
from langchain.messages import AIMessage, HumanMessage, ToolMessage

# 模型发起的工具调用
ai_message = AIMessage(
    content=[],
    tool_calls=[
        {
            "name": "get_weather",
            "args": {"location": "San Francisco"},
            "id": "call_123",
        }
    ],
)

# 执行工具，把结果包成 ToolMessage
tool_message = ToolMessage(
    content="Sunny, 72°F",
    tool_call_id="call_123",  # 必须与调用 id 一致
    name="get_weather",
)

# 把工具结果交回模型
response = model.invoke(
    [
        HumanMessage("What's the weather in San Francisco?"),
        ai_message,
        tool_message,
    ]
)
```

#### artifact：只给应用看的数据

`artifact` 里的内容**不会发给模型**，但应用侧可以读到。
适合放原始文档 ID、页码这类「模型用不上、但渲染页面要用」的元数据：

```python
tool_message = ToolMessage(
    content="It was the best of times, it was the worst of times.",
    tool_call_id="call_123",
    name="search_books",
    artifact={"document_id": "doc_123", "page": 0},
)

tool_message.content    # 发给模型的正文
tool_message.artifact   # {'document_id': 'doc_123', 'page': 0}，应用侧可见
```

> [!TIP]
> RAG 场景特别适合用 `artifact`：模型看到的是检索出来的正文，
> 文档 ID 放进 `artifact`，前端就能据此渲染出处和跳转链接。

## 消息内容

`content` 是消息的负载，属性上是「松类型」的，可以是字符串，
也可以是字典列表。LangChain 对它的定义是：

1. 一个字符串
2. 一组 provider 原生格式的内容块
3. 一组 LangChain **标准内容块**

```python
from langchain.messages import HumanMessage

# 字符串内容
message = HumanMessage("Hello, how are you?")

# provider 原生格式（以 OpenAI 为例）
message = HumanMessage(
    content=[
        {"type": "text", "text": "Hello, how are you?"},
        {"type": "image_url", "image_url": {"url": "https://example.com/image.jpg"}},
    ]
)

# LangChain 标准内容块
message = HumanMessage(
    content_blocks=[
        {"type": "text", "text": "Hello, how are you?"},
        {"type": "image", "url": "https://example.com/image.jpg"},
    ]
)
```

> [!TIP]
> 用 `content_blocks=` 初始化消息时，`content` 依然会被填上，
> 只是提供了一个类型安全的写法。

### content_blocks：标准化的那一层

消息对象实现了 `content_blocks` 属性，它会**惰性解析** `content`，
把各家 provider 的原生格式翻译成同一套标准块。

这就是跨 provider 的关键：Anthropic 的 `thinking` 和 OpenAI 的
`reasoning`，解析出来都是 `reasoning` 块。

```python
from langchain.messages import AIMessage

# OpenAI 风格
message = AIMessage(
    content=[
        {
            "type": "reasoning",
            "id": "rs_abc123",
            "summary": [
                {"type": "summary_text", "text": "summary 1"},
                {"type": "summary_text", "text": "summary 2"},
            ],
        },
        {"type": "text", "text": "...", "id": "msg_abc123"},
    ],
    response_metadata={"model_provider": "openai"},
)
message.content_blocks
# [
#     {'type': 'reasoning', 'id': 'rs_abc123', 'reasoning': 'summary 1'},
#     {'type': 'reasoning', 'id': 'rs_abc123', 'reasoning': 'summary 2'},
#     {'type': 'text', 'text': '...', 'id': 'msg_abc123'},
# ]
```

```python
# Anthropic 风格
message = AIMessage(
    content=[
        {"type": "thinking", "thinking": "...", "signature": "WaUjzkyp..."},
        {"type": "text", "text": "..."},
    ],
    response_metadata={"model_provider": "anthropic"},
)
message.content_blocks
# [
#     {'type': 'reasoning', 'reasoning': '...', 'extras': {'signature': 'WaUjzkyp...'}},
#     {'type': 'text', 'text': '...'},
# ]
```

> [!WARNING]
> **百炼的 OpenAI 兼容接口不会把思考内容映射进 `content_blocks`。**
> 实测 `deepseek-v4-pro` 开启深度思考后，`content_blocks` 里只有 `text` 块，
> 思考内容只能从 `usage_metadata` 的 `reasoning` 数字上看出来。

### 内容块速查表

标准内容块都是「带类型的字典」，常用的有这么几种：

| 类型 | 用途 | 关键字段 |
| --- | --- | --- |
| `text` | 普通文本 | `text`、`annotations` |
| `reasoning` | 模型的推理过程 | `reasoning`、`extras` |
| `refusal` | 模型明确拒答 | `refusal`、`extras` |
| `image` | 图片 | `url` / `base64` / `file_id`、`mime_type` |
| `audio` | 音频 | `url` / `base64` / `file_id`、`mime_type` |
| `video` | 视频 | `url` / `base64` / `file_id`、`mime_type` |
| `file` | 通用文件（PDF 等） | `url` / `base64` / `file_id`、`mime_type` |
| `text-plain` | 文档正文（txt、md） | `text`、`mime_type` |
| `tool_call` | 工具调用请求 | `id`、`name`、`args` |
| `tool_call_chunk` | 流式工具调用分片 | `id`、`name`、`args`、`index` |
| `invalid_tool_call` | 解析失败的工具调用 | `name`、`args`、`error` |
| `server_tool_call` | 服务端执行的工具调用 | `id`、`name`、`args` |
| `server_tool_result` | 服务端工具的执行结果 | `tool_call_id`、`status`、`output` |
| `non_standard` | provider 私有结构的逃生舱 | `value` |

> [!TIP]
> `non_standard` 是给「provider 有、但 LangChain 还没标准化」的结构用的。
> 但别依赖它一直待在 `non_standard` 里——随着 `langchain-core` 增加新的标准块类型，
> 对应的数据会从 `non_standard` 挪进新类型。
> 判断逻辑要写成 `if block["type"] == ...`，不要按载荷内容猜。

### 多模态

图片、文件、音频、视频统一用标准内容块表达，来源有三种写法：

```python
# 从 URL
message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "Describe the content of this image."},
        {"type": "image", "url": "https://example.com/path/to/image.jpg"},
    ],
}

# 从 base64 数据
message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "Describe the content of this image."},
        {
            "type": "image",
            "base64": "AAAAIGZ0eXBtcDQyAAAAAGlzb21tcDQy...",
            "mime_type": "image/jpeg",
        },
    ],
}

# 从 provider 托管的 File ID
message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "Describe the content of this image."},
        {"type": "image", "file_id": "file-abc123"},
    ],
}
```

PDF、音频、视频换成 `file`、`audio`、`video` 即可，字段结构一致。

> [!WARNING]
> 不是所有模型都支持所有文件类型。
> 另外 OpenAI 的接口要求传 PDF 时必须带文件名，
> 具体看所用 provider 的参考文档。

### 序列化

消息可以序列化成普通字典存起来，再反序列化回消息对象，
用于持久化会话历史、恢复会话。

```python
from langchain.messages import HumanMessage
from langchain_core.load import dumpd, load

message = HumanMessage("What is the capital of France?")

# 序列化成普通字典
serialized = dumpd(message)
# {'lc': 1, 'type': 'constructor',
#  'id': ['langchain', 'schema', 'messages', 'HumanMessage'],
#  'kwargs': {'content': 'What is the capital of France?', 'type': 'human'}}

# 反序列化回消息对象
restored = load(serialized)
```

> [!WARNING]
> **`load()` 会实例化 Python 对象，等同于执行一份配置。**
> 永远不要对不可信或未鉴权的数据直接调用 `load()`。
> 反序列化外部数据时显式限制允许的类型：
>
> ```python
> restored = load(serialized, allowed_objects="messages")
> ```

> [!NOTE]
> `load()` 目前还处在 beta，默认的 `allowed_objects` 取值将来会变，
> 调用时会有一行 `LangChainPendingDeprecationWarning`。
> 显式传参可以把这行警告也一并消掉。

## 与聊天模型配合

聊天模型接受一个消息序列作为输入，返回一条 `AIMessage`。
交互通常是**无状态**的，所以简单的对话循环就是
「每次都把累积的消息列表重新发过去」：

```python
from langchain.messages import HumanMessage, SystemMessage

history = [SystemMessage("你是一位中文技术助手，回答简洁清晰。")]

for question in ["我叫小海，记住我的名字。", "我叫什么名字？"]:
    history.append(HumanMessage(question))
    response = model.invoke(history)
    history.append(response)
    print(response.text)
```

实测输出：

```
用户：我叫小海，记住我的名字。
助手：好的，小海。我记住了，有什么可以帮你的吗？
      用量：输入 35 / 输出 14 / 合计 49

用户：我叫什么名字？
助手：你叫小海。
      用量：输入 57 / 输出 5 / 合计 62
```

注意每轮的**输入 token 在涨**（35 → 57），
因为历史越积越长，每次都要整体重发。
这就是「上下文窗口」问题，生产环境要配合裁剪或摘要，
官方对应的文档是
[short-term-memory](https://docs.langchain.com/oss/python/langchain/short-term-memory)。

> [!TIP]
> 这个循环就是 LangGraph / `create_agent` 的底层机制。
> 智能体只是在「模型 → 工具 → 模型」之间多插了几轮，
> 并用 checkpointer 把历史持久化下来。

## 总结

消息这一层的 API 很薄，但有几个容易踩的点：

1. **用 `content_blocks` 读内容**，`content` 只是原始负载。
   它是唯一能同时兼容文本、推理过程、工具调用和各家 provider 的读法。
2. **输入消息没有 id**，只有模型响应才会被自动补上 `lc_run--` 前缀的 id，
   provider 的请求 id 在 `response_metadata["id"]` 里。
3. **流式分片默认不带 token 用量**，要统计得显式传 `stream_usage=True`。
4. **`ToolMessage.tool_call_id` 必须和 `AIMessage.tool_calls` 对上**，
   对不上模型就不知道这个结果是给哪次调用的。
5. **`artifact` 里的数据不会发给模型**，正好用来放文档 ID 这类
   「模型用不上、应用要用」的元数据。
6. **`load()` 不要用在不可信数据上**，反序列化外部数据时显式传
   `allowed_objects="messages"`。
7. **百炼的 OpenAI 兼容接口不映射推理内容**，
   想看思考过程只能看 `usage_metadata` 里的 `reasoning` 数字。
