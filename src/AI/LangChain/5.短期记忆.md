## 前言

本篇记录 LangChain 1.x **短期记忆（Short-term memory）** 的完整用法

官方文档：[LangChain Short-term memory](https://docs.langchain.com/oss/python/langchain/short-term-memory)

前面几篇都在讲「怎么让模型干活」：
A01 讲怎么把模型接进来，A02 讲模型本身，A03 讲消息怎么组织，A04 讲工具怎么用。
但一直有个问题没解决——**模型本身是无状态的**，
每调用一次它就「失忆」一次，第二次调用它不记得你叫小海。

短期记忆就是来解决这件事的：
把对话状态存起来，下次调用时再读出来。
听起来只是「存个历史」，但真做起来会发现一堆细节：
存哪儿？存多久？怎么防止撑爆上下文窗口？
删消息的时候把工具调用删坏了怎么办？

这一篇把官方文档的每个点都跑了一遍，示例代码见仓库中的 `A05-langchain-short-term-memory`。
仍然使用阿里云百炼（DashScope）平台的 **deepseek-v4-pro-0813** 模型，
通过 OpenAI 兼容模式接入。

### 核心概念

| 概念 | 说明 |
| --- | --- |
| `checkpointer` | 检查点，把图状态持久化到数据库或内存 |
| `thread_id` | 会话编号，决定读写哪一份记忆 |
| `AgentState` | 默认的短期记忆容器，核心是 `messages` 字段 |
| `state_schema` | 扩展 `AgentState`，加自己的字段 |
| `RemoveMessage` | 从状态里删除消息 |
| `@before_model` | 调用模型前处理历史（裁剪） |
| `@after_model` | 模型返回后处理历史（删除、校验） |
| `SummarizationMiddleware` | 内置的摘要中间件 |
| `ToolRuntime` | 工具里读写状态的入口 |
| `Command` | 工具返回值之一，可以顺手更新状态 |
| `@dynamic_prompt` | 动态生成系统提示词 |

## 记忆是怎么工作的

### 两行代码

短期记忆的核心就两件事：**挂一个 checkpointer**，**调用时带上 thread_id**。

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=model,
    tools=[get_user_info],
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "1"}}
agent.invoke({"messages": [{"role": "user", "content": "Hi! My name is Bob."}]}, config)
agent.invoke({"messages": [{"role": "user", "content": "What's my name?"}]}, config)
```

实测输出：

```
=== 没有 checkpointer：每次调用都是新对话 ===
回答： 目前我这边没有查到你的用户档案信息，所以还不知道你的名字哦。方便的话，可以告诉我你叫什么吗？

=== 挂上 checkpointer：同一个 thread_id 共享记忆 ===
回答： 你好，小海！很高兴认识你～
回答： 你叫小海呀～ 这是你之前告诉我的名字。
```

没有 checkpointer 时，第二次调用完全不知道第一次说过什么；
挂上之后，同一个 `thread_id` 的两次调用共享同一份历史。

> [!NOTE]
> 短期记忆是 **agent 状态的一部分**，不是独立的组件。
> 状态存在图的 state 里，靠 checkpointer 落盘，
> 所以不同 thread 之间天然隔离，同一个 thread 可以随时恢复。

> [!TIP]
> 想记住**跨会话**的信息（用户偏好、知识库），要用
> [长期记忆](https://docs.langchain.com/oss/python/langchain/long-term-memory)——
> 那是 `store` 的活儿，不是 `checkpointer` 的活儿。
> 两者别搞混：
>
> | | 短期记忆 | 长期记忆 |
> | --- | --- | --- |
> | 载体 | `checkpointer` + `thread_id` | `store` + namespace |
> | 范围 | 单个 thread 内部 | 跨 thread、跨会话 |

### thread_id 就是记忆的边界

同一个智能体实例可以同时服务很多用户，靠的就是 `thread_id`：

```python
agent.invoke({"messages": [...]}, {"configurable": {"thread_id": "user-alice"}})
agent.invoke({"messages": [...]}, {"configurable": {"thread_id": "user-bob"}})
```

实测两个会话互不干扰：

```
[user-alice] 你叫 **Alice**，做的是**后端开发**。
[user-bob] 你叫 **Bob**，做的是**前端开发**工作。
```

> [!WARNING]
> **thread_id 必须稳定。**
> 如果每次请求都生成一个新的 thread_id（比如用 UUID），
> 那就等于每次都是新会话，记忆完全失效。
> 正确的做法是用「会话 ID」或「用户 ID + 会话 ID」这类可复现的值。

### 生产环境要用数据库检查点

`InMemorySaver` 只活在当前进程里，程序一退出记忆就没了。
生产环境要用基于数据库的实现，官方推荐 PostgreSQL：

```bash
pip install -U langgraph-checkpoint-postgres "psycopg[binary]"
```

```python
from langchain.agents import create_agent
from langgraph.checkpoint.postgres import PostgresSaver

DB_URI = "postgresql://postgres:postgres@localhost:5432/postgres?sslmode=disable"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()  # 自动在 PostgreSQL 里建表
    agent = create_agent(
        "gpt-5.5",
        tools=[get_user_info],
        checkpointer=checkpointer,
    )
```

没有 PostgreSQL 也能演示持久化，SQLite 检查点同样能跨进程恢复：

```python
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string("data/memory.db") as checkpointer:
    agent = create_agent(model=model, checkpointer=checkpointer)
```

实测「进程一写入 → 进程二重新打开」：

```
--- 进程一：写入记忆（数据库 data/memory.db）---
写入完成，线程列表： ['persist-demo']

--- 进程二：重新打开同一个数据库 ---
--- 重启后恢复的 thread_id=persist-demo（共 2 条）---
 1. [human] 我叫小海，记住我的名字。
 2. [ai] 好的，小海！我已经记住你的名字了。
回答： 你叫小海。
```

> [!NOTE]
> 官方还提供 Azure Cosmos DB、Redis 等检查点实现，
> 完整清单见 [checkpointer libraries](https://docs.langchain.com/oss/python/langgraph/checkpointers#checkpointer-libraries)。

## 扩展记忆的内容

默认情况下，agent 用 `AgentState` 管理短期记忆，核心就是 `messages` 字段。
想多记点东西，继承它加字段即可：

```python
from langchain.agents import AgentState, create_agent


class CustomerState(AgentState):
    user_id: str
    preferences: dict


agent = create_agent(
    model=model,
    tools=[get_user_info],
    state_schema=CustomerState,
    checkpointer=InMemorySaver(),
)

result = agent.invoke(
    {
        "messages": [{"role": "user", "content": "你好"}],
        "user_id": "user_123",
        "preferences": {"theme": "dark"},
    },
    {"configurable": {"thread_id": "1"}},
)
```

自定义字段和消息一样会跟着检查点持久化，
所以它们属于**短期记忆**（跟着 thread 走），不是长期记忆。

实测这些字段在下一轮对话里还在，而且工具能直接读到：

```
=== 第二次调用：只发消息，自定义字段仍在，工具里能读到 ===
助手： 我帮你查过了，你当前的设置如下：

- **主题**：深色模式（dark）
- **语言**：中文（zh）

=== 状态快照 ===
user_id    = user_123
preferences = {'theme': 'dark', 'language': 'zh'}
```

> [!NOTE]
> 自定义字段的**初始值来自 `invoke` 的入参**。
> 第二次调用只发消息时，这些字段会从检查点里恢复，不会被重置。

## 长对话怎么不撑爆上下文

有了记忆之后，新的问题来了：对话一长，消息历史就会超出模型的上下文窗口。
官方给了四种常见解法：

> [card] [裁剪消息](#裁剪消息)
>
> 丢掉最早或最晚的 N 条消息

> [card] [删除消息](#删除消息)
>
> 从状态里永久删掉某些消息

> [card] [摘要消息](#摘要消息)
>
> 把老消息压缩成一段摘要

> [card] 自定义策略
>
> 自己写中间件过滤消息

### 裁剪消息

最直接的做法：只保留最近 N 条（外加最早那条最初的提问），其余丢掉。

```python
from langchain.agents import create_agent
from langchain.agents.middleware import before_model
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES


@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    """Keep only the last few messages to fit context window."""
    messages = state["messages"]
    if len(messages) <= 3:
        return None  # No changes needed

    first_msg = messages[0]
    recent_messages = messages[-3:] if len(messages) % 2 == 0 else messages[-4:]
    new_messages = [first_msg] + recent_messages

    return {
        "messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),
            *new_messages,
        ]
    }


agent = create_agent(
    model=model,
    tools=[...],
    middleware=[trim_messages],
    checkpointer=InMemorySaver(),
)
```

关键在于 `RemoveMessage(id=REMOVE_ALL_MESSAGES)`：
它表示「清空现有历史」，然后你把想保留的消息重新写回去。

实测裁剪过程：

```
用户：再具体说说 checkpointer 是什么。
    [中间件] 裁剪消息：7 条 -> 5 条
助手： checkpointer 主要出现在 LangGraph 中，用于持久化图的状态……
```

裁剪完的历史：

```
--- 裁剪后的历史（共 6 条）---
 1. [human] 你好，我叫小海。
 2. [ai] 在 LangChain 生态中，**checkpointer** 主要出现在 **LangGraph** 中……
 3. [human] 那 thread_id 呢？
 4. [ai] 在 LangGraph 中，thread_id 是**标识一个独立对话会话的唯一字符串**……
 5. [human] 我叫什么名字？
 6. [ai] 你叫小海。
```

> [!TIP]
> **记得保住最早那条消息。**
> 用户最初的需求往往就在第一条消息里，
> 裁掉它之后模型会「失忆」——问它「我叫什么名字」就答不出来了。
> 官方示例里的 `keep_first` 就是干这个的。

> [!WARNING]
> **裁剪必须保证工具调用配对完整。**
>
> 模型提供方有两条硬性要求：
>
> * 带 `tool_calls` 的 AI 消息后面必须跟着对应的 `ToolMessage`；
> * `ToolMessage` 不能凭空出现，必须能找到发起它的工具调用。
>
> 如果裁剪正好切在「AI 发起工具调用」和「工具返回结果」中间，
> 轻则模型报错，重则行为诡异。
>
> 本项目在 `src/memory/messages.py` 里做了双向清理：
> 先丢掉找不到调用方的 `ToolMessage`，
> 再丢掉缺少返回值的 AI 消息：
>
> ```python
> def sanitize_tool_pairs(messages):
>     # 找出所有已声明的工具调用 id
>     declared_ids = {c["id"] for m in messages for c in (m.tool_calls or [])}
>     # 丢掉孤立的工具结果
>     ...
>     # 丢掉缺少返回值的 AI 消息
>     ...
> ```

### 删除消息

裁剪是「把太长的历史变短」，删除是「把不想留下的内容彻底抹掉」——
比如敏感信息、错误的中间推理，或者干脆清空整个历史重新开始。

删单条：

```python
from langchain.messages import RemoveMessage


def delete_messages(state):
    messages = state["messages"]
    if len(messages) > 2:
        # remove the earliest two messages
        return {"messages": [RemoveMessage(id=m.id) for m in messages[:2]]}
```

删全部：

```python
from langgraph.graph.message import REMOVE_ALL_MESSAGES


def delete_messages(state):
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES)]}
```

挂到 `@after_model` 上，就能做「模型说了不该说的话就立刻删掉」：

```python
from langchain.agents.middleware import after_model


@after_model
def remove_sensitive_reply(state: AgentState, runtime: Runtime) -> dict | None:
    """Remove messages containing sensitive words."""
    last_message = state["messages"][-1]
    if any(word in last_message.content for word in ("密码", "身份证", "银行卡")):
        return {"messages": [RemoveMessage(id=last_message.id)]}
    return None
```

实测：

```
=== 触发敏感词过滤 ===
    [中间件] 回复包含敏感词，已从历史中删除
--- 敏感回复已被删除（共 3 条）---
 1. [human] 你好，我叫小海。
 2. [ai] 你好，小海！很高兴认识你……
 3. [human] 我的银行卡号是 6222 0000 0000 0000。
```

> [!WARNING]
> **清空整个历史要用 `update_state`，不要用 `invoke`。**
>
> ```python
> agent.update_state(config, {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES)]})
> ```
>
> `invoke` 会把这一串 `RemoveMessage` 当作新一轮输入发给模型，
> 而此时历史已被清空，模型收到一个空消息列表，
> 百炼会直接报：
>
> ```
> InternalError.Algo.InvalidParameter: Role must be in ["user", "assistant", "system", ...]
> and the role in last message must be in ["user", "function", "tool"]
> ```
>
> `update_state` 直接改写检查点，不触发模型调用，才是清空历史的正确姿势。

> [!NOTE]
> 删除消息时**要保证剩下的历史是合法的**：
> 有些提供方要求历史必须以 `user` 消息开头，
> 绝大多数要求带工具调用的 AI 消息后面必须跟工具结果。

### 摘要消息

裁剪和删除都会**丢信息**。摘要的做法是：让模型把老消息浓缩成一段话，
用这段话替换原来的历史，既省 token 又保留关键信息。

LangChain 1.x 内置了 `SummarizationMiddleware`，不用自己写：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model="gpt-5.5",
    tools=[...],
    middleware=[
        SummarizationMiddleware(
            model="gpt-5.4-mini",     # 用便宜的小模型做摘要
            trigger=("tokens", 4000), # 超过 4000 tokens 触发
            keep=("messages", 20)     # 摘要后保留最近 20 条原始消息
        )
    ],
    checkpointer=checkpointer,
)
```

三个参数：

| 参数 | 作用 | 可选值 |
| --- | --- | --- |
| `trigger` | 什么时候触发摘要 | `("tokens", N)` / `("messages", N)` / `("fraction", 0.8)` |
| `keep` | 摘要之后保留多少条原始消息 | 同上 |
| `model` | 用哪个模型做摘要 | 建议用便宜的小模型 |

摘要写回状态时是一条带 `lc_source="summarization"` 标记的 `HumanMessage`，
内容是 `Here is a summary of the conversation to date:` 加上摘要正文。
实测历史长度就是这样被压住的：

```
    [历史] 2 条消息，约 33 tokens（含 0 条摘要）
    [历史] 4 条消息，约 198 tokens（含 0 条摘要）
    [历史] 6 条消息，约 835 tokens（含 0 条摘要）
    [历史] 8 条消息，约 1353 tokens（含 0 条摘要）
    [历史] 6 条消息，约 2021 tokens（含 1 条摘要）
    [历史] 8 条消息，约 3235 tokens（含 1 条摘要）
    [历史] 6 条消息，约 2834 tokens（含 1 条摘要）
```

可以看到消息数在 6 ~ 8 条之间来回摆动，永远不会无限增长。

> [!TIP]
> **摘要用小模型。**
> 摘要本身是一次额外的 LLM 调用，
> 用贵模型做纯属浪费——`gpt-5.4-mini` 之类的完全够用。
> 本项目示例里用的是百炼的 `deepseek-v4-pro-0813`，
> 生产环境建议单独配一个便宜的模型。

> [!NOTE]
> 摘要不是免费的：每触发一次就多一次模型调用和一次延迟。
> `trigger` 设得太激进（比如 20 条消息就触发）反而更慢更贵。
> 官方文档推荐的做法是**先用裁剪兜底，再用摘要兜底**——
> 裁剪是零成本的，摘要只在真的撑不住时才用。

## 在工具里读写记忆

### 读

工具想拿到「用户之前说了什么」，通过 `runtime.state` 取。

```python
from langchain.tools import ToolRuntime, tool


@tool
def recall_user_name(runtime: ToolRuntime) -> str:
    """回顾用户之前自报过的名字。"""
    messages = runtime.state.get("messages", [])
    for message in reversed(messages):
        if isinstance(message, HumanMessage):
            ...
    return "用户还没有说过名字。"
```

`runtime` 参数**不会出现在给模型看的 schema 里**，模型不会误以为要传参：

```
recall_user_name.args = {}
```

实测效果：

```
用户：你好，我叫小海。
助手： 你好，小海！很高兴认识你～

用户：我叫什么名字？
助手： 你叫**小海**呀！这是你刚见面时告诉我的名字～

用户：我们聊了多少轮了？
助手： 我们目前已经聊了 **3 轮**啦！
```

### 写

工具不只返回结果，还能顺手**更新图状态**。做法是返回 `Command`：

```python
from langchain.messages import ToolMessage
from langchain.tools import ToolRuntime, tool
from langgraph.types import Command


class ProfileState(AgentState):
    nickname: str


@tool
def remember_nickname(nickname: str, runtime: ToolRuntime) -> Command:
    """把用户的昵称写进会话状态。"""
    return Command(
        update={
            "nickname": nickname,
            "messages": [
                ToolMessage(
                    content=f"已记住昵称：{nickname}",
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
```

实测：

```
=== 让模型把昵称写进状态 ===
助手： 好的，阿海！我已经记住你的昵称啦～

=== 状态里的自定义字段 ===
nickname = 阿海

=== 下一轮模型能从状态里读到昵称 ===
助手： 你的昵称是「阿海」。
```

> [!WARNING]
> **`Command.update` 里必须带一条 `tool_call_id` 匹配的 `ToolMessage`。**
>
> 消息历史里的每个工具调用都要有对应的 `ToolMessage`，
> 少了这条 `ToolNode` 会直接抛 `ValueError`：
>
> ```
> ValueError: Expected to have a matching ToolMessage in Command.update for tool 'remember_nickname',
> got: []. Every tool call (LLM requesting to call a tool) in the message history MUST have a
> corresponding ToolMessage.
> ```
>
> `tool_call_id` 从 `runtime.tool_call_id` 拿，**不要自己编**。

## 动态生成系统提示词

系统提示词不一定要是死字符串。`@dynamic_prompt` 让它随运行时状态变化：

```python
from langchain.agents.middleware import ModelRequest, dynamic_prompt


@dynamic_prompt
def dynamic_system_prompt(request: ModelRequest) -> str:
    user_name = request.runtime.context["user_name"]
    return f"You are a helpful assistant. Address the user as {user_name}."


agent = create_agent(
    model=model,
    tools=[get_weather],
    middleware=[dynamic_system_prompt],
    context_schema=CustomContext,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is the weather in SF?"}]},
    context=CustomContext(user_name="John Smith"),
)
```

两种常见数据来源：

| 来源 | 是什么 | 典型用途 |
| --- | --- | --- |
| `request.runtime.context` | 调用时传入的不可变上下文 | 用户 ID、角色、租户 |
| `request.state` | 当前线程的短期记忆 | 历史消息、自定义字段 |

> [!NOTE]
> `context` 和 `state` 的区别在 A04 讲过，这里再强调一次：
> **context 是单次运行的**，每次 `invoke` 都可以不一样；
> **state 是跟着 thread 走的**，同一个 thread 内一直有效。
> 想按用户身份变化（用户等级、会员状态）用 context，
> 想按对话进展变化（聊到哪了、记住了什么）用 state。

## 一个完整的例子

把上面所有能力拼一起——一个电商客服智能体：

```python
from langchain.agents import AgentState, create_agent
from langchain.agents.middleware import before_model, dynamic_prompt
from langchain.messages import RemoveMessage, ToolMessage
from langchain.tools import ToolRuntime, tool
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.types import Command


class ShopState(AgentState):
    user_id: str
    member_level: str
    last_queried_order: str


@tool
def query_order(order_id: str, runtime: ToolRuntime) -> Command:
    """查询订单状态，并把订单号写进会话状态。"""
    return Command(
        update={
            "last_queried_order": order_id,
            "messages": [
                ToolMessage(content=content, tool_call_id=runtime.tool_call_id)
            ],
        }
    )


@before_model
def trim_history(state: ShopState, runtime: Any) -> dict[str, Any] | None:
    """调用模型前裁剪历史。"""
    messages = list(state["messages"])
    if len(messages) <= 6:
        return None
    kept = keep_recent_messages(messages, 6, keep_first=True)
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *kept]}


@dynamic_prompt
def shop_system_prompt(request: Any) -> str:
    """按会员等级生成不同的服务话术。"""
    level = (request.state or {}).get("member_level", "普通会员")
    return f"你是电商平台的客服助手。当前用户的会员等级是「{level}」。"
```

跑起来的效果：

```
用户：你好，我是黄金会员。
助手： 您好！感谢您的咨询。作为黄金会员，您目前可享受以下权益：积分双倍、
      每月三张 **8 折优惠券**，以及优先发货。

用户：帮我查一下订单 A1001。
助手： 已为您查询到订单 A1001 的信息：商品为机械键盘，金额 499 元，状态为 **已发货**。

用户：那 A1002 呢？
    [中间件] 裁剪历史：9 -> 7 条
助手： 已为您查询到订单 A1002 的信息：商品为显示器支架，金额 159 元，状态为 **待付款**。

=== 会话状态 ===
user_id           = u001
member_level      = 黄金会员
last_queried_order = A1002
```

> [!NOTE]
> `[中间件] 裁剪历史` 这一行出现了两次不是 bug——
> 带工具的轮次要调用两次模型（第一次决定调工具，第二次总结），
> `@before_model` 每次调用模型前都会跑一次。

## 总结

短期记忆的 API 很薄——挂个 `checkpointer`、传个 `thread_id` 就完事了。
但要做对，有几个必须注意的点：

1. **`checkpointer` + `thread_id` 缺一不可**。
   前者决定「存不存」，后者决定「存哪儿」。
2. **thread_id 要稳定**，用随机 UUID 等于每次新会话。
3. **生产环境用数据库检查点**，
   `InMemorySaver` 一重启就丢。
4. **自定义状态字段属于短期记忆**，
   跟着 thread 走，跨会话要用 store。
5. **裁剪历史要保住最初那条消息**，否则模型会「失忆」。
6. **裁剪必须修好工具调用配对**，
   切在工具调用中间会直接让模型报错。
7. **删除消息后要保证历史合法**，
   清空整个历史用 `update_state` 而不是 `invoke`。
8. **摘要是最后一道防线**，
   前面先用裁剪兜底，摘要用便宜的小模型。
9. **工具读状态用 `runtime.state`，
   写状态返回 `Command`**，
   别忘了带 `tool_call_id` 匹配的 `ToolMessage`。
10. **系统提示词可以动态生成**，
    按 context 变还是按 state 变，取决于数据的生命周期。
