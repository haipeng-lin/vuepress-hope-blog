## 前言

本篇记录 LangChain 1.x **模型（Models）** API 的完整用法

官方文档：[LangChain Models](https://docs.langchain.com/oss/python/langchain/models)

模型是智能体的推理引擎，负责决定调用哪个工具、如何解读工具结果、
什么时候给出最终答案。A01 讲的是「怎么把模型接进来」，
本篇讲的是**接进来之后能怎么用**。

仍然使用阿里云百炼（DashScope）平台的 **deepseek-v4-pro-0813** 模型，
通过 OpenAI 兼容模式接入。示例代码见仓库中的 `A02-langchain-model`。

### 核心概念

| 概念 | 说明 |
| --- | --- |
| `init_chat_model` | 统一的模型初始化入口，支持按字符串或模型类创建 |
| `invoke` | 一次性调用，等模型生成完完整响应 |
| `stream` | 流式调用，边生成边返回分片 |
| `batch` | 批量并行调用多个独立请求 |
| `bind_tools` | 把工具的 schema 交给模型，让它能发起工具调用 |
| `with_structured_output` | 让模型按指定 schema 返回结构化对象 |
| `content_blocks` | LangChain 1.x 推荐的输出读取方式，统一处理富内容 |
| `configurable_fields` | 把模型的部分参数推迟到运行时再决定 |

## 初始化模型

### init_chat_model

最省事的方式是 `init_chat_model`，它把各个 provider 的差异都封在后面：

```python
import os
from langchain.chat_models import init_chat_model

model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    api_key=os.environ["DASHSCOPE_API_KEY"],
    temperature=0.3,
)
```

`{provider}:{model}` 格式一次写清「用哪个 provider 的哪个模型」。
百炼提供的是 OpenAI 兼容接口，所以 provider 写 `openai`，
再把 `base_url` 指向百炼的兼容模式地址。

> [!WARNING]
> 和 A01 一样，不要同时传 `model_provider="openai"`。
> 两种写法同时存在时，`openai:` 前缀不会被剥离，
> 最终模型名会变成 `openai:deepseek-v4-pro-0813`，请求直接返回 404：
>
> ```
> Error code: 404 - The model `openai:deepseek-v4-pro-0813` does not exist
> ```

也可以完全不用 `init_chat_model`，直接用模型类，两者完全等价：

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="deepseek-v4-pro-0813",
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    api_key=os.environ["DASHSCOPE_API_KEY"],
)
```

### 切换模型

换模型只需要改模型名，接口调用方式完全不变：

```python
model = init_chat_model("openai:qwen-plus", base_url=..., api_key=...)
```

百炼上常用的几个模型：

| 模型 | 说明 |
| --- | --- |
| `deepseek-v4-pro-0813` | 默认模型，支持深度思考、工具调用、结构化输出 |
| `qwen-plus` | 通用对话模型，速度快、成本低，适合做「简单模型」 |
| `qwen3-vl-plus` | 视觉模型，支持图片输入 |

### 模型画像

`profile` 属性描述了模型支持哪些能力（上下文窗口、是否支持工具调用、
是否支持图片输入等），数据来自 [models.dev](https://models.dev/)：

```python
model.profile
# {
#   "max_input_tokens": 400000,
#   "image_inputs": True,
#   "reasoning_output": True,
#   "tool_calling": True,
# }
```

> [!NOTE]
> 百炼的模型不在 models.dev 的收录范围里，所以实际取到的是 `None`。
> 画像数据可以用来动态适配模型能力——比如按上下文窗口决定要不要做摘要压缩、
> 按是否支持原生结构化输出来选策略。

## 模型参数

| 参数 | 说明 |
| --- | --- |
| `model` | 模型名，必填 |
| `api_key` | 鉴权密钥，通常走环境变量 |
| `temperature` | 采样温度，越高越发散 |
| `max_tokens` | 限制输出长度 |
| `timeout` | 请求超时（秒） |
| `max_retries` | 失败重试次数，LangChain 默认 6 |

### temperature

温度控制输出的随机性。实际影响通常没有想象中大，
但需要稳定复现的结果（比如结构化抽取）建议设成 `0` 或 `0.1`。

### max_tokens 与推理 token

这是百炼上最容易踩的坑。`deepseek-v4-pro` 默认开启深度思考，
**思考过程消耗的 token 与正文共用 `max_tokens` 预算**：

```python
model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    max_tokens=50,
)

response = model.invoke("介绍一下 LangChain 的历史。")
print(response.content)      # 空字符串！
print(response.usage_metadata)
# {'output_tokens': 50, 'output_token_details': {'reasoning': 50}}
```

50 个 token 全被思考过程用掉了，正文一个字都没轮到。
在结构化输出场景更严重，会直接抛异常：

```
openai.LengthFinishReasonError: Could not parse response content
as the length limit was reached
```

两种解决办法：

1. 关掉深度思考（结构化输出场景推荐）

   ```python
   model = init_chat_model(
       "openai:deepseek-v4-pro-0813",
       base_url=...,
       api_key=...,
       max_tokens=1000,
       extra_body={"enable_thinking": False},
   )
   ```

2. 把 `max_tokens` 给足，给思考过程留出空间

> [!TIP]
> `init_chat_model` 的 `timeout` 最终落到 `ChatOpenAI.request_timeout` 上，
> 读取时要用对属性名：
>
> ```python
> print(model.request_timeout, model.max_retries)
> # 60.0 3
> ```

### 重试与超时

LangChain 对网络错误、429 限流、5xx 服务端错误自动做指数退避重试；
401 鉴权失败、404 模型不存在这类客户端错误不会重试。

默认重试 6 次，在网络不稳定的长流程里可能等太久。
可以按场景调整：

```python
model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    timeout=120,
    max_retries=10,   # 官方文档建议不稳定网络下提到 10~15
)
```

### 限流器

很多平台都有 QPS 限制。`rate_limiter` 控制请求发送频率：

```python
from langchain.rate_limiters import InMemoryRateLimiter

rate_limiter = InMemoryRateLimiter(
    requests_per_second=0.1,   # 每 10 秒 1 个请求
    check_every_n_seconds=0.1, # 每 100ms 检查一次是否放行
    max_bucket_size=10,        # 允许的突发请求数
)

model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    rate_limiter=rate_limiter,
)
```

> [!WARNING]
> 限流器只能限制**请求次数**，不能限制请求体大小。

## 调用模型

### 三种输入形式

`invoke` 接受三种输入：

```python
# 1. 单个字符串
response = model.invoke("为什么鹦鹉的羽毛是彩色的？")

# 2. 字典列表，显式写清角色
conversation = [
    {"role": "system", "content": "你是一位中文助手。"},
    {"role": "user", "content": "请用一句话介绍 LangChain。"},
]
response = model.invoke(conversation)

# 3. 消息对象，类型更明确
from langchain.messages import HumanMessage, SystemMessage

conversation = [
    SystemMessage("你是一位中文助手。"),
    HumanMessage("请用一句话介绍 LangChain。"),
]
response = model.invoke(conversation)
```

### 返回值结构

返回的**不是字符串**，而是一个 `AIMessage`：

```python
type(response)             # <class 'langchain_core.messages.ai.AIMessage'>
response.content           # 文本内容
response.content_blocks    # 内容块列表，推荐的读取方式
response.usage_metadata    # token 用量
response.response_metadata # 模型名、finish_reason 等
```

`content_blocks` 是 LangChain 1.x 推荐的读取方式，
它把文本、推理过程、工具调用统一成同一种结构：

```python
response.content_blocks
# [
#   {"type": "reasoning", "reasoning": "..."},
#   {"type": "text", "text": "..."},
#   {"type": "tool_call", "name": "get_weather", "args": {...}, "id": "..."},
# ]
```

> [!TIP]
> 如果 `invoke` 的返回值直接就是字符串，说明用的是旧版的
> 文本补全 LLM 而不是聊天模型。LangChain 的聊天模型类都带 `Chat` 前缀，
> 比如 `ChatOpenAI`。

### RunnableConfig

调用时可以传 `config`，做运行时的控制与标记：

```python
response = model.invoke(
    "讲个笑话",
    config={
        "run_name": "joke_generation",       # 本次运行的名字
        "tags": ["humor", "demo"],           # 会被子调用继承
        "metadata": {"user_id": "123"},      # 会被子调用继承
        "callbacks": [my_callback_handler],  # 回调
    },
)
```

这些字段配合 LangSmith 追踪特别有用：可以按 `tags` 过滤、
按 `metadata` 关联业务数据、按 `run_name` 定位具体环节。

## 流式输出

`stream` 返回的是 `AIMessageChunk` 迭代器，不是完整消息：

```python
for chunk in model.stream("为什么鹦鹉的羽毛是彩色的？"):
    print(chunk.text, end="", flush=True)
```

### 按内容块分流

流式场景下文本、推理过程、工具调用会混在同一条流里，
按 `content_blocks` 的类型分流处理：

```python
for chunk in model.stream("天空是什么颜色？"):
    for block in chunk.content_blocks:
        if block["type"] == "reasoning" and (reasoning := block.get("reasoning")):
            print(f"推理：{reasoning}")
        elif block["type"] == "tool_call_chunk":
            print(f"工具调用分片：{block}")
        elif block["type"] == "text":
            print(block["text"])
```

### 累加分片

分片可以用 `+` 累加成一条完整消息：

```python
full = None
for chunk in model.stream("天空是什么颜色？"):
    full = chunk if full is None else full + chunk
    print(full.text)

# The sky is typically blue
```

累加后的消息和 `invoke` 的结果等价，可以直接塞回消息历史。

### 语义级事件

需要按事件类型过滤时，用 `astream_events` 更方便：

```python
async for event in model.astream_events("你好"):
    if event["event"] == "on_chat_model_start":
        print(f"输入：{event['data']['input']}")
    elif event["event"] == "on_chat_model_stream":
        print(f"增量：{event['data']['chunk'].text}")
    elif event["event"] == "on_chat_model_end":
        print(f"完整消息：{event['data']['output'].text}")
```

> [!TIP]
> 在 LangGraph 智能体里，节点内即使写的是 `model.invoke()`，
> 只要外层用的是 `stream()`，LangChain 会自动切换到内部流式模式。
> 这样不用改节点代码，整个应用（包含智能体内部）都能实时输出。

## 批量调用

多个互不依赖的请求用 `batch` 并行发送，能显著提升吞吐：

```python
responses = model.batch([
    "为什么鹦鹉的羽毛是彩色的？",
    "飞机是怎么飞起来的？",
    "什么是量子计算？",
])
for response in responses:
    print(response.content)
```

> [!NOTE]
> `batch()` 是**客户端并行**，和 OpenAI / Anthropic 服务端的批量 API 是两回事。

想谁先完成就先拿到谁，用 `batch_as_completed`：

```python
for response in model.batch_as_completed([...]):
    print(response)
```

它返回的是 `(下标, 响应)` 二元组，因为完成顺序和输入顺序不一定一致，
需要靠下标还原原始顺序。

并发数用 `max_concurrency` 控制：

```python
model.batch(
    list_of_inputs,
    config={"max_concurrency": 5},
)
```

## 工具调用

### bind_tools

把工具绑定给模型，模型就能自己决定调用哪个：

```python
from langchain.tools import tool


@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气信息。"""
    return f"{city}当前天气：晴，气温 26℃。"


model_with_tools = model.bind_tools([get_weather])

response = model_with_tools.invoke("杭州的天气怎么样？")
for tool_call in response.tool_calls:
    print(f"工具：{tool_call['name']}")
    print(f"参数：{tool_call['args']}")
```

> [!NOTE]
> 单独使用模型时，模型只是**请求**调用工具，执行得自己做。
> 用智能体（`create_agent`）的话，这个循环由智能体负责。

### 手动执行工具循环

工具调用是一个「模型 → 执行工具 → 回填结果 → 模型总结」的循环：

```python
tools = [get_weather]
tools_by_name = {tool.name: tool for tool in tools}
model_with_tools = model.bind_tools(tools)

messages = [{"role": "user", "content": "杭州的天气怎么样？"}]

# 第一步：模型生成工具调用请求
ai_msg = model_with_tools.invoke(messages)
messages.append(ai_msg)

# 第二步：执行工具，把结果作为 ToolMessage 追加回去
for tool_call in ai_msg.tool_calls:
    tool = tools_by_name[tool_call["name"]]
    tool_result = tool.invoke(tool_call)
    messages.append(tool_result)

# 第三步：把工具结果交回模型
final_response = model_with_tools.invoke(messages)
print(final_response.text)
```

工具返回的 `ToolMessage` 里带 `tool_call_id`，模型据此把结果和请求对应起来。

### 并行工具调用

模型可以一次请求多个互不依赖的工具：

```python
response = model_with_tools.invoke("杭州和成都的天气怎么样？")
print(response.tool_calls)
# [
#   {'name': 'get_weather', 'args': {'city': '杭州'}, 'id': 'call_1'},
#   {'name': 'get_weather', 'args': {'city': '成都'}, 'id': 'call_2'},
# ]
```

需要串行时关掉并行：

```python
model.bind_tools([get_weather], parallel_tool_calls=False)
```

### 流式工具调用

流式场景下工具调用是分片到达的，要用 `+` 累加：

```python
gathered = None
for chunk in model_with_tools.stream("杭州的天气怎么样？"):
    gathered = chunk if gathered is None else gathered + chunk

print(gathered.tool_calls)
# [{'name': 'get_weather', 'args': {'city': '杭州'}, 'id': 'call_...'}]
```

## 结构化输出

### 三种 schema 写法

**Pydantic** —— 功能最全，自带字段校验和描述：

```python
from pydantic import BaseModel, Field


class Movie(BaseModel):
    """一部电影的基本信息。"""

    title: str = Field(description="电影名称")
    year: int = Field(description="上映年份")
    director: str = Field(description="导演姓名")
    rating: float = Field(description="评分，满分 10 分")


model_with_structure = model.with_structured_output(Movie)
response = model_with_structure.invoke("请给出电影《星际穿越》的详细信息。")
print(response)  # Movie(title='星际穿越', year=2014, ...)
```

**TypedDict** —— 更轻量，不需要运行时校验：

```python
from typing_extensions import Annotated, TypedDict


class MovieDict(TypedDict):
    """一部电影的基本信息。"""

    title: Annotated[str, ..., "电影名称"]
    year: Annotated[int, ..., "上映年份"]
    director: Annotated[str, ..., "导演姓名"]
    rating: Annotated[float, ..., "评分，满分 10 分"]


model_with_structure = model.with_structured_output(MovieDict)
response = model_with_structure.invoke("请给出电影《星际穿越》的详细信息。")
print(response)  # {'title': '星际穿越', ...}
```

**JSON Schema** —— 跨语言互操作时最通用：

```python
json_schema = {
    "title": "Movie",
    "type": "object",
    "properties": {
        "title": {"type": "string", "description": "电影名称"},
        "year": {"type": "integer", "description": "上映年份"},
    },
    "required": ["title", "year"],
}

model_with_structure = model.with_structured_output(json_schema, method="json_schema")
```

三种方法对应服务端的两种机制：

| 方法 | 说明 |
| --- | --- |
| `json_schema` | 服务端原生支持的语法约束解码 |
| `function_calling` | 借助强制工具调用来产出结构化结果 |
| `json_mode` | 只保证是合法 JSON，schema 要写进提示词 |

### 嵌套结构

schema 可以嵌套：

```python
class Actor(BaseModel):
    name: str
    role: str


class MovieDetails(BaseModel):
    title: str
    year: int
    cast: list[Actor]
    genres: list[str]
```

> [!WARNING]
> 百炼的结构化输出基于**语法约束解码**，服务端要把 JSON Schema 编译成语法。
> schema 里带**对象数组**（`list[SomeModel]`）时容易出问题：
> 轻则返回空列表，重则触发长度限制。稳妥做法是拆成简单结构多次调用，
> 或者改用 `json_schema` 方法。

### 同时拿到原文和解析结果

`include_raw=True` 会同时返回原始消息和解析结果，
既能读 token 用量，也能在解析失败时排查：

```python
model_with_structure = model.with_structured_output(Movie, include_raw=True)
response = model_with_structure.invoke("请给出电影《星际穿越》的详细信息。")

response["parsed"]          # Movie(...)
response["parsing_error"]   # 解析失败时的异常对象
response["raw"]             # 原始的 AIMessage
```

### 模型拒答

provider 把「拒答」当成一次成功响应返回，而不是报错。
普通调用返回带 `refusal` 内容块的消息，
`with_structured_output` 则会抛 `ModelRefusalError`：

```python
from langchain_core.exceptions import ModelRefusalError

try:
    response = model_with_structure.invoke("...")
except ModelRefusalError as error:
    print(error)              # Model refused to produce the requested output
    refused = error.raw_message
```

用 `include_raw=True` 时不会抛异常，而是放进 `parsing_error` 里。

## 多模态

输入图片用 content block 表达：

```python
message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "请描述这张图片。"},
        {"type": "image_url", "image_url": {"url": IMAGE_URL}},
    ],
}
response = model.invoke([message])
```

本地图片转成 base64 内联传入，格式是 data URL：

```python
{"type": "image_url", "image_url": {"url": "data:image/png;base64,<编码后的内容>"}}
```

模型返回图片时，`content_blocks` 里会出现 `image` 类型的内容块：

```python
response.content_blocks
# [
#     {"type": "text", "text": "这是你要的图片："},
#     {"type": "image", "base64": "...", "mime_type": "image/jpeg"},
# ]
```

> [!NOTE]
> 不是所有模型都支持视觉。实测百炼上 `deepseek-v4-pro` 收到图片后会回复
> 「我无法查看图片」，换 `qwen3-vl-plus` 才能正常识别。

## 推理

推理模型会把复杂问题拆成小步骤思考，代价是额外的 reasoning token。

```python
response = model.invoke("小明有 5 个苹果，又买了 3 个，然后吃了 2 个。他有几个？")
print(response.content)
print(response.usage_metadata)
# {'output_tokens': 158, 'output_token_details': {'reasoning': 107}}
```

不需要思考时可以关掉，响应快很多：

```python
model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    extra_body={"enable_thinking": False},
)
```

实测对比：

| 配置 | 输入 token | 输出 token | 其中推理 |
| --- | --- | --- | --- |
| 开启思考 | 114 | 158 | 107 |
| 关闭思考 | 35 | 97 | 0 |

> [!NOTE]
> OpenAI 兼容接口不会把思考内容映射进 `content_blocks`，
> 只能从 token 统计里看到它消耗了多少。
> Anthropic、OpenAI 的 reasoning 模型会把思考内容放进
> `content_blocks` 的 `reasoning` 类型里。

部分 provider 还支持指定思考强度 `reasoning_effort`
（`'low'` / `'medium'` / `'high'`），可以在模型构造时或单次调用时设置：

```python
response = model.invoke("...", reasoning_effort="high")
```

这个参数需要 `langchain-core>=1.5.2` 以及对应的 partner 包版本。

## 可配置模型

### configurable_fields

把模型的某些参数推迟到运行时再决定：

```python
configurable_model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    temperature=0.3,
    configurable_fields=("model", "temperature"),
)

configurable_model.invoke(
    "用一句话介绍 LangChain。",
    config={"configurable": {"model": "openai:qwen-plus"}},
)
```

> [!WARNING]
> 运行时传入的模型名**必须带 provider 前缀**。
> 写成 `"qwen-plus"` 时，`init_chat_model` 会按名字猜 provider，
> 试图加载没装的 `langchain-deepseek`：
>
> ```
> ImportError: Initializing ChatDeepSeek requires the langchain-deepseek package
> ```

一条链里有多个模型时，用 `config_prefix` 区分：

```python
first_model = init_chat_model(
    "openai:deepseek-v4-pro-0813",
    base_url=...,
    api_key=...,
    configurable_fields=("model", "model_provider", "temperature", "max_tokens"),
    config_prefix="first",
)

first_model.invoke(
    "用一句话介绍 LangChain。",
    config={
        "configurable": {
            "first_model": "openai:qwen-plus",
            "first_temperature": 0.5,
            "first_max_tokens": 100,
        }
    },
)
```

### 动态模型选择

用 `@wrap_model_call` 中间件，可以在运行时根据上下文换模型：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import ModelRequest, ModelResponse, wrap_model_call

basic_model = init_chat_model("openai:qwen-plus", base_url=..., api_key=...)
advanced_model = init_chat_model("openai:deepseek-v4-pro-0813", base_url=..., api_key=...)


@wrap_model_call
def dynamic_model_selection(request: ModelRequest, handler) -> ModelResponse:
    """按对话复杂度选择模型。"""
    message_count = len(request.state["messages"])
    model = advanced_model if message_count > 10 else basic_model
    return handler(request.override(model=model))


agent = create_agent(
    model=basic_model,
    tools=[],
    middleware=[dynamic_model_selection],
)
```

> [!WARNING]
> 已经 `bind_tools` 过的模型（预绑定模型）不支持结构化输出。
> 需要「动态选型 + 结构化输出」时，中间件里传的模型不能是预绑定的。

## 错误处理

各个集成包抛的都是 `langchain_core.exceptions` 里的标准异常，
同时继承 LangChain 基类和 provider SDK 的异常，两边都能捕获：

| 异常 | 含义 | 可重试 |
| --- | --- | --- |
| `ModelAuthenticationError` | API Key 缺失或失效 | 否 |
| `ModelPermissionDeniedError` | 凭证没有权限 | 否 |
| `ModelInvalidRequestError` | 服务端拒绝了请求 | 否 |
| `ModelNotFoundError` | 模型不存在 | 否 |
| `ModelRateLimitError` | 触发限流 | 是 |
| `ModelAPIError` | 服务端故障 | 是 |
| `ModelConnectionError` | 连不上服务 | 是 |
| `ModelTimeoutError` | 请求超时 | 是 |
| `ContextOverflowError` | 输入超出上下文长度 | 否 |

每个异常都带 `is_retryable` 属性，重试中间件默认按它判断：

```python
from langchain_core.exceptions import ModelTimeoutError

try:
    response = model.invoke("你好")
except ModelTimeoutError:
    print("超时了")
```

```python
response.usage_metadata
```

想在应用层做聚合统计，用回调或上下文管理器：

```python
from langchain_core.callbacks import get_usage_metadata_callback

with get_usage_metadata_callback() as cb:
    model_1.invoke("你好")
    model_2.invoke("你好")

# }
```

## 总结

LangChain 1.x 的模型接口收敛得很干净，核心就是
**`init_chat_model` + `invoke` / `stream` / `batch`** 三个方法，
加上 `bind_tools` 和 `with_structured_output` 两个扩展点。但落到具体 provider 上，
有几个必须注意的点：

1. **百炼接入**用 `init_chat_model("openai:...")`，别叠加 `model_provider`。
2. **推理 token 和正文共用 `max_tokens`**，预算给小了会输出为空，
   结构化输出场景还会直接抛 `LengthFinishReasonError`。
3. **运行时换模型要带 provider 前缀**，否则 `init_chat_model` 会猜错 provider。
4. **结构化输出不要和工具放同一次请求**，百炼的语法编译扛不住；
   嵌套 schema 里的对象数组也不稳。
5. **读取输出用 `content_blocks`**，它是唯一能同时兼容文本、
   推理过程和工具调用的方式。
6. **异常分可重试和不可重试两类**，靠 `is_retryable` 判断，别一股脑重试。
