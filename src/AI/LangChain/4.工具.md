## 前言

本篇记录 LangChain 1.x **工具（Tools）** 的完整用法

官方文档：[LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools)

工具是智能体对外「伸手」的方式——查天气、查数据库、算数、
改状态，全靠它。A01 讲的是「怎么把模型接进来」，
A02 讲的是「模型本身怎么用」，A03 讲的是「消息怎么组织」，
本篇讲的是**智能体与外部世界之间的那层接口**：
工具怎么定义、怎么被模型调用、怎么拿到运行时的上下文、怎么返回结果。

仍然使用阿里云百炼（DashScope）平台的 **deepseek-v4-pro-0813** 模型，
通过 OpenAI 兼容模式接入。示例代码见仓库中的 `A04-langchain-tool`。

### 核心概念

| 概念 | 说明 |
| --- | --- |
| `@tool` | 把普通 Python 函数包装成模型可调用的工具 |
| 工具 schema | 由函数签名与 docstring 生成的入参结构 |
| `ToolRuntime` | 工具运行时的统一入口，拿到 state / context / store |
| `Command` | 工具返回值之一，可以在返回结果的同时更新图状态 |
| `return_direct` | 工具结果直接作为最终答案，跳过后续模型调用 |
| `wrap_tool_call` | 中间件钩子，用来接管工具执行（重试、错误处理） |
| `wrap_model_call` | 中间件钩子，用来在运行时增删工具 |

## 定义工具

### 最简单的写法

工具就是一个**带类型注解和 docstring 的普通函数**。
LangChain 把它包装成 `StructuredTool`，把签名转成 JSON Schema，
把 docstring 转成工具描述：

```python
from langchain.tools import tool


@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气信息。"""
    return f"{city}当前天气：晴，气温 26℃。"
```

两件事是**必需**的：

1. **类型注解**定义了工具的输入 schema，没有注解就没有 schema；
2. **docstring** 就是工具描述，它决定了模型什么时候会调用这个工具。

可以直接在 REPL 里检查模型看到的东西：

```python
get_weather.name          # 'get_weather'
get_weather.description   # '查询指定城市的实时天气信息。'
get_weather.args
# {'city': {'title': 'City', 'type': 'string'}}
```

> [!NOTE]
> `description` 不只是给人看的，它**是模型选择工具的主要依据**。
> 写得越具体（什么时候用、参数什么含义），模型选得越准。

### 自定义名称与描述

工具名默认取函数名，可以显式覆盖：

```python
@tool("web_search")
def search(query: str) -> str:
    """搜索网络上的公开信息。"""
    return f"「{query}」的搜索结果。"


@tool("calculator", description="执行算术运算。任何数学计算问题都可以使用它。")
def calc(expression: str) -> str:
    """计算表达式。"""
    return str(eval(expression))
```

> [!WARNING]
> **工具名请用 `snake_case`**（`web_search` 而不是 `Web Search`）。
> 部分模型提供方会拒绝带空格或特殊字符的名字，
> 只用字母、数字、下划线和连字符可以最大化跨提供方兼容性。

> [!TIP]
> 两个工具重名是最难查的一类 bug——模型会随机挑一个调用，
> 而且不报错。命名时带上动词前缀（`query_order`、`get_weather`）不容易撞。

### 定义入参 schema

参数变多、需要默认值或需要更精确的字段说明时，
用 `args_schema` 显式指定输入结构。

**Pydantic 模型**——功能最全，自带校验与字段描述：

```python
from pydantic import BaseModel, Field
from typing import Literal


class WeatherInput(BaseModel):
    """Input for weather queries."""

    location: str = Field(description="City name or coordinates")
    units: Literal["celsius", "fahrenheit"] = Field(
        default="celsius",
        description="Temperature unit preference",
    )
    include_forecast: bool = Field(
        default=False,
        description="Include 5-day forecast",
    )


@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and optional forecast."""
    ...
```

`Literal` 还能限定取值范围，传了非法值会直接被拦下：

```python
get_weather.invoke({"location": "上海", "units": "kelvin"})
# ValidationError: Input should be 'celsius' or 'fahrenheit'
```

**JSON Schema**——跨语言互操作时最通用：

```python
weather_schema = {
    "type": "object",
    "properties": {
        "location": {"type": "string"},
        "units": {"type": "string"},
        "include_forecast": {"type": "boolean"},
    },
    "required": ["location", "units", "include_forecast"],
}


@tool(args_schema=weather_schema)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    ...
```

三种写法对比：

| 写法 | 优点 | 适用场景 |
| --- | --- | --- |
| 函数签名 | 最简洁 | 参数少、类型明确 |
| Pydantic 模型 | 校验 + 字段描述 + 默认值 | 参数多、需要约束取值 |
| JSON Schema | 跨语言通用 | 与非 Python 服务对接 |

> [!TIP]
> docstring 里的 `Args:` 段落也可以直接变成参数描述，
> 前提是显式开启 `parse_docstring=True`：
>
> ```python
> @tool(parse_docstring=True)
> def search_database(query: str, limit: int = 10) -> str:
>     """Search the customer database for records matching the query.
>
>     Args:
>         query: Search terms to look for
>         limit: Maximum number of results to return
>     """
> ```
>
> 这样 `query` 和 `limit` 的 description 就自动填好了。

### 保留的参数名

下面两个参数名被框架占用，**不能**拿来当业务参数：

| 参数名 | 用途 |
| --- | --- |
| `config` | 接收 `RunnableConfig` |
| `runtime` | 接收 `ToolRuntime` |

用了会在运行时报错。实测把 `runtime` 当普通字符串参数：

```python
@tool
def f(runtime: str) -> str:
    """占用 runtime 名字"""
    return f"got {runtime}"
```

模型调用时工具会直接失败：

```
Error invoking tool 'f' with kwargs {'runtime': 'runtime'} with error:
```

`config` 同理，而且报的是另一种错：

```
TypeError: f() missing 1 required positional argument: 'config'
```

> [!TIP]
> 如果确实要接收 `RunnableConfig`，
> 就把类型标成 `RunnableConfig` 而不是 `str`——
> 框架会识别它并自动注入，模型看不到这个参数。

## 工具调用循环

工具调用是个「模型 → 执行工具 → 回填结果 → 模型总结」的循环。
用 `create_agent` 时这个循环由框架负责：

```python
from langchain.agents import create_agent

agent = create_agent(
    model,
    tools=[get_weather, query_order],
    system_prompt="你是一位电商客服助手。",
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "订单 A1001 的状态和快递单号是什么？"}]}
)
```

实测消息轨迹：

```
[human] 订单 A1001 的状态和快递单号是什么？
[ai] 调用 query_order({'order_id': 'A1001'}) id=call_8ddb022c7dbb4c4f9c1589ce
[tool] {"order_id": "A1001", "customer": "小海", "item": "机械键盘",
        "amount": 499, "status": "已发货", "tracking_no": "SF1234567890"}
[ai] 订单 A1001 的查询结果如下：
    - **订单状态**：已发货
    - **快递单号**：SF1234567890
```

想看清每一步发生了什么，就手写一遍这个循环：

```python
tools_by_name = {tool.name: tool for tool in tools}
model_with_tools = model.bind_tools(tools)

messages = [HumanMessage(question)]

# 第一步：模型生成工具调用请求
ai_msg = model_with_tools.invoke(messages)
messages.append(ai_msg)

# 第二步：执行工具，结果作为 ToolMessage 追加回去
for tool_call in ai_msg.tool_calls:
    tool = tools_by_name[tool_call["name"]]
    messages.append(tool.invoke(tool_call))

# 第三步：把工具结果交回模型
final_response = model_with_tools.invoke(messages)
```

> [!NOTE]
> 单独用模型时，模型只是**请求**调用工具，执行得自己做。
> 用智能体的话，这个循环由 `ToolNode` 负责。

## 访问上下文

工具最有价值的地方在于能拿到运行时的信息。
LangChain 1.x 把这些统一收敛到 `ToolRuntime` 一个对象上。

### ToolRuntime

在工具签名里加一个 `runtime: ToolRuntime` 参数，
调用时框架会自动注入，**而且这个参数不会出现在给模型看的 schema 里**：

```python
from langchain.tools import tool, ToolRuntime


@tool
def get_user_preference(pref_name: str, runtime: ToolRuntime) -> str:
    """Get a user preference value."""
    preferences = runtime.state.get("user_preferences", {})
    return preferences.get(pref_name, "Not set")
```

模型看到的 schema 里只有 `pref_name`：

```python
get_user_preference.args
# {'pref_name': {'title': 'Pref Name', 'type': 'string'}}
```

`ToolRuntime` 上能拿到的东西：

| 属性 | 说明 | 典型用途 |
| --- | --- | --- |
| `state` | 当前图状态（短期记忆） | 读消息历史、读自定义字段 |
| `context` | 调用时传入的不可变上下文 | 按用户身份个性化 |
| `store` | 跨会话的长期记忆 | 保存用户偏好、维护知识库 |
| `stream_writer` | 工具执行期间推送进度 | 显示加载动画、进度条 |
| `tool_call_id` | 本次调用的 id | 构造 `ToolMessage` |
| `config` | 本次执行的 `RunnableConfig` | 读 tags、metadata、callbacks |
| `execution_info` | thread_id / run_id / 重试次数 | 追踪执行、按次数调整行为 |
| `server_info` | LangGraph Server 上的助手与用户 | 取 assistant_id、登录用户 |
| `tools` | 当前可用的全部工具 | 工具互相调用 |

### 短期记忆：State

`runtime.state` 就是当前对话的图状态：

```python
from langchain.messages import HumanMessage


@tool
def get_last_user_message(runtime: ToolRuntime) -> str:
    """Get the most recent message from the user."""
    messages = runtime.state["messages"]
    for message in reversed(messages):
        if isinstance(message, HumanMessage):
            return message.content
    return "No user messages found"
```

### 更新状态：Command

工具不只返回结果，还能**顺手改状态**。这时返回值是 `Command`：

```python
from langchain.agents import AgentState
from langchain.messages import ToolMessage
from langchain.tools import ToolRuntime, tool
from langgraph.types import Command


class CustomState(AgentState):
    user_name: str


@tool
def set_user_name(new_name: str, runtime: ToolRuntime[None, CustomState]) -> Command:
    """Set the user's name in the conversation state."""
    return Command(
        update={
            "user_name": new_name,
            "messages": [
                ToolMessage(
                    content=f"User name set to {new_name}.",
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
```

自定义状态字段要通过 `state_schema` 声明给智能体：

```python
agent = create_agent(model, tools=[set_user_name], state_schema=CustomState)
```

> [!WARNING]
> **`Command.update` 里必须带一条 `tool_call_id` 匹配的 `ToolMessage`。**
> 消息历史里的每个工具调用都要有对应的 `ToolMessage`，
> 少了这条 `ToolNode` 会直接抛 `ValueError`。
>
> `tool_call_id` 从 `runtime.tool_call_id` 拿，不要自己编。
>
> 实测漏掉时的报错：
>
> ```
> ValueError: Expected to have a matching ToolMessage in Command.update for tool 'set_user_name',
> got: []. Every tool call (LLM requesting to call a tool) in the message history MUST have a
> corresponding ToolMessage.
> ```

> [!TIP]
> 状态字段可能被**并行工具调用**同时写入。
> 这时候要给字段定义 [reducer](https://docs.langchain.com/oss/python/langgraph/graph-api#reducers)，
> 让 LangGraph 知道冲突时怎么合并。

### 上下文：Context

`context` 是**调用时传入**的不可变数据，作用域是单次运行。
适合放用户 ID、会话信息这类不该在对话中变化的东西：

```python
from dataclasses import dataclass


@dataclass
class UserContext:
    user_id: str


@tool
def get_account_info(runtime: ToolRuntime[UserContext]) -> str:
    """Get the current user's account information."""
    return f"用户 {runtime.context.user_id} 的账户信息"
```

创建智能体时声明 schema，调用时传对象：

```python
agent = create_agent(
    model,
    tools=[get_account_info],
    context_schema=UserContext,
    checkpointer=InMemorySaver(),
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What's my current balance?"}]},
    config={"configurable": {"thread_id": thread_id}},
    context=UserContext(user_id="user123"),
)
```

> [!NOTE]
> `thread_id` 划分的是**对话**（消息历史与检查点），
> `context` 携带的是**本次运行**的数据。
> 生产环境通常两个一起传：一个稳定的 `thread_id` 加每次 invoke 的 `context`。

> [!WARNING]
> **写了 context 就要带上泛型参数**（`ToolRuntime[UserContext]`）。
> 裸的 `ToolRuntime` 声明的 context 类型是 `None`，
> 而实际注入的是 `UserContext` 对象，
> Pydantic 在序列化运行状态时会刷一串
> `PydanticSerializationUnexpectedValue` 警告。

### 长期记忆：Store

`store` 是跨会话的持久化存储，用 namespace/key 组织数据：

```python
from langgraph.store.memory import InMemoryStore


@tool
def save_user_info(user_id: str, name: str, age: int, email: str, runtime: ToolRuntime) -> str:
    """Save user info."""
    runtime.store.put(("users",), user_id, {"name": name, "age": age, "email": email})
    return "Successfully saved user info."


@tool
def get_user_info(user_id: str, runtime: ToolRuntime) -> str:
    """Look up user info."""
    item = runtime.store.get(("users",), user_id)
    return str(item.value) if item else "Unknown user"
```

智能体层面挂上 store：

```python
agent = create_agent(model, tools=[get_user_info, save_user_info], store=InMemoryStore())
```

实测第一次调用写入、第二次调用（换了新的 thread_id）照样能读到：

```
第一次调用（写入）：
第二次调用（跨会话读取）：
已查到用户 abc123 的信息：
- 姓名：小海
- 年龄：25
- 邮箱：xiaohai@example.com
```

> [!TIP]
> 生产环境请把 `InMemoryStore` 换成 `PostgresStore`、`MongoDBStore` 或 `RedisStore`。
> `InMemorySaver` 同理，换成持久化 checkpointer。

### 流式输出：stream_writer

工具跑得慢的时候，界面一片空白体验很差。
`runtime.stream_writer` 可以在执行途中推送进度：

```python
@tool
def get_weather(city: str, runtime: ToolRuntime) -> str:
    """Get weather for a given city."""
    writer = runtime.stream_writer
    writer(f"Looking up data for city: {city}")
    writer(f"Acquired data for city: {city}")
    return f"It's always sunny in {city}!"
```

用 `stream_mode="custom"` 接收：

```python
for chunk in agent.stream(inputs, config=config, stream_mode="custom"):
    print(chunk)
```

实测输出：

```
[自定义流] 正在收集「LangChain」的资料……
[自定义流] 资料收集完成，正在生成报告……
```

> [!NOTE]
> `runtime.stream_writer` 只能在 LangGraph 执行上下文里用，
> 也就是必须在智能体或图里调用，不能脱离智能体单独跑。

### 执行信息：execution_info

`runtime.execution_info` 提供这次执行的「身份信息」：

```python
@tool
def log_execution_context(runtime: ToolRuntime) -> str:
    """Log execution identity information."""
    info = runtime.execution_info
    print(f"Thread: {info.thread_id}, Run: {info.run_id}")
    print(f"Attempt: {info.node_attempt}")
    return "done"
```

实测 `ExecutionInfo` 的字段：

```python
ExecutionInfo(
    checkpoint_id='1f1da795-...',
    checkpoint_ns='tools:4ce924f4-...',
    task_id='4ce924f4-...',
    thread_id='t1',
    run_id=None,
    node_attempt=1,
    node_first_attempt_time=1794035013.07,
)
```

> [!NOTE]
> 需要 `langgraph>=1.1.5`。

### 服务端信息：server_info

跑在 LangGraph Server 上时，还能拿到助手 ID 与登录用户：

```python
@tool
def get_assistant_scoped_data(runtime: ToolRuntime) -> str:
    """Fetch data scoped to the current assistant."""
    server = runtime.server_info
    if server is not None:
        print(f"Assistant: {server.assistant_id}, Graph: {server.graph_id}")
        if server.user is not None:
            print(f"User: {server.user.identity}")
    return "done"
```

本地开发或测试时 `server_info` 是 `None`，
所以**一定要判空**再取值。

### 迁移旧写法

早期文档用的是 `InjectedState`、`InjectedStore`、`get_runtime()`、
`InjectedToolCallId` 这几套注入方式。
现在统一收敛到 `ToolRuntime`：

```python
# 旧写法
from langchain.tools import tool, InjectedState


@tool
def summarize(state: InjectedState) -> str:
    """Summarize the conversation."""
    messages = state["messages"]
    return f"Conversation length: {len(messages)} messages."


# 新写法
from langchain.tools import tool, ToolRuntime


@tool
def summarize(runtime: ToolRuntime) -> str:
    """Summarize the conversation."""
    messages = runtime.state["messages"]
    return f"Conversation length: {len(messages)} messages."
```

## 工具返回值

工具可以返回四种东西，各有适用场景。

### 返回字符串

最常见，结果本身就是给人看的文本：

```python
@tool
def get_weather(city: str) -> str:
    """Get weather for a city."""
    return f"It is currently sunny in {city}."
```

返回值会被转成 `ToolMessage`，模型读到后决定下一步做什么。

### 返回对象

结果是结构化数据、模型要按字段推理时，返回 dict：

```python
@tool
def get_weather_data(city: str) -> dict:
    """Get structured weather data for a city."""
    return {"city": city, "temperature_c": 22, "conditions": "sunny"}
```

实测模型能正确地从字段里取值：

```
[tool] {"order_id": "A1001", "customer": "小海", "item": "机械键盘",
        "amount": 499, "status": "已发货", "tracking_no": "SF1234567890"}
[ai] 订单 A1001 当前状态是 **已发货**。
    - 商品：机械键盘
    - 金额：499 元
    - 快递单号：SF1234567890
```

> [!TIP]
> 和返回字符串相比，返回 dict 让模型能引用具体字段，
> 也方便你的应用代码直接从结果里取数据。
> 两者都不会直接更新图状态——想更新状态得用 `Command`。

### 返回多模态内容

工具可以返回[标准内容块](https://docs.langchain.com/oss/python/langchain/messages#standard-content-blocks)，
一次带上文字和图片：

```python
@tool
def capture_screenshot() -> list[dict]:
    """Capture a screenshot of the current page."""
    return [
        {"type": "text", "text": "Screenshot of the current page:"},
        {"type": "image", "url": "https://example.com/page.png"},
    ]
```

实测 `ToolMessage.content` 就是内容块列表：

```
[tool] [{'type': 'text', 'text': '截图'}, {'type': 'image', 'url': 'https://example.com/a.png'}]
```

> [!NOTE]
> 模型必须支持你返回的模态。
> 百炼上 `deepseek-v4-pro` 不支持图片输入，
> 换 `qwen3-vl-plus` 才能正常识别（见 A03）。

### 返回 Command

前面讲过了：`Command` 让你在返回结果的同时更新状态。

### return_direct：直接返回

工具结果本身就是最终答案时，加 `return_direct=True`，
智能体直接把它返回给调用方，**不再走一次模型**：

```python
@tool(return_direct=True)
def fetch_order_status(order_id: str) -> str:
    """Fetch the current status of a customer order."""
    return f"Order {order_id} is shipped and will arrive in 2 days."
```

实测消息轨迹只有三条，末尾没有 AI 总结：

```
[human] 订单 12345 的状态？
[ai] 调用 fetch_order_status({'order_id': '12345'}) id=call_58e38e5d...
[tool] 订单 12345 已发货，预计 2 天内送达。

消息条数 = 3（没有最后那条 AI 总结）
```

> [!WARNING]
> **只有当工具结果不需要再加工时才适合用 `return_direct`。**
> 模型没机会读这个结果，也就不能改写、总结或接着调用别的工具。

> [!WARNING]
> **并行调用时只有「全部」工具都是 `return_direct` 才提前结束。**
> 混着调用时智能体会回到模型，让它基于所有结果继续推理。
> 这一点官方文档里有明确说明，很容易踩。

### Command + return_direct

两者可以一起用。`Command` 不会自动转成 `ToolMessage`，
所以 `update` 里仍要自己带上匹配 `tool_call_id` 的 `ToolMessage`：

```python
@tool(return_direct=True)
def fetch_and_store_order(order_id: str, runtime: ToolRuntime) -> Command:
    """Fetch order status and store it in state."""
    status = f"Order {order_id} is shipped and will arrive in 2 days."
    return Command(
        update={
            "last_order_status": status,
            "messages": [
                ToolMessage(content=status, tool_call_id=runtime.tool_call_id)
            ],
        }
    )
```

要写回**父图**则设置 `graph=Command.PARENT`，
此时因为执行已经离开当前图，ToolMessage 的要求会被解除。

## 错误处理

工具抛异常时，默认行为是**整轮对话直接失败**。
实测不加任何处理：

```
整轮失败：ValueError
订单号「A9999」不存在，只支持查询 A1001。
```

LangChain 1.x 用**中间件**来接管这件事。
`wrap_tool_call` 钩子可以在工具执行前后插手：

```python
from collections.abc import Callable

from langchain.agents import create_agent
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools.tool_node import ToolCallRequest


@wrap_tool_call
def handle_tool_errors(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage],
) -> ToolMessage:
    """Convert tool exceptions into ToolMessages the model can handle."""
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"Tool error: Please check your input and try again. ({e})",
            tool_call_id=request.tool_call["id"],
        )


agent = create_agent(model=model, tools=[...], middleware=[handle_tool_errors])
```

加上之后，模型看到的是一条正常的工具消息，
可以自己纠正参数或向用户解释：

```
[ai] 调用 query_order({'order_id': 'A9999'}) id=call_9b5da38b...
[tool] 工具执行失败：订单号「A9999」不存在，只支持查询 A1001。请检查输入参数后重试。
[ai] 查询订单 A9999 失败，因为该订单号不存在。
```

> [!TIP]
> 中间件可以叠加，而且**先定义的在最外层**。
> 常见组合是「重试中间件 + 错误转消息中间件」：
> 先重试，重试仍失败再把异常转成 `ToolMessage` 返回给模型。
>
> ```python
> @wrap_tool_call
> def retry_twice(request, handler):
>     for _ in range(3):
>         try:
>             return handler(request)
>         except Exception:
>             pass
>     raise
> ```

## 动态工具选择

工具不是越多越好。太多会撑爆上下文，也容易让模型选错。
动态选择有两条路子。

### 过滤预注册工具

所有工具在创建智能体时就已知，运行时按状态、权限、偏好决定暴露哪几个。
用 `wrap_model_call` 中间件：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from typing import Callable


@wrap_model_call
def role_based_tools(
    request: ModelRequest,
    handler: Callable[[ModelRequest], ModelResponse],
) -> ModelResponse:
    """Filter tools based on Runtime Context permissions."""
    context = request.runtime.context if request.runtime else None
    user_role = getattr(context, "user_role", "viewer")

    if user_role == "admin":
        pass  # 管理员看到全部工具
    elif user_role == "editor":
        request = request.override(
            tools=[t for t in request.tools if t.name != "delete_data"]
        )
    else:
        request = request.override(
            tools=[t for t in request.tools if t.name.startswith("read_")]
        )

    return handler(request)
```

实测不同角色暴露的工具：

```
角色 admin   暴露的工具：['public_search', 'private_search', 'delete_data']
角色 editor  暴露的工具：['public_search', 'private_search']
角色 viewer  暴露的工具：['public_search']
```

被过滤掉的工具模型是**完全看不到**的——
它不会知道 `private_search` 存在，所以也不会去调用它。

按 **Store 里的用户偏好**过滤也是一样的写法，
只要把 `request.runtime.store` 里的 feature flags 读出来即可。

### 运行时注册工具

工具本身是运行时才发现的（比如从 MCP 服务器加载、
按用户数据动态生成），就要同时**挂载工具**和**接管它的执行**。
这需要两个钩子：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import AgentMiddleware, ModelRequest, ToolCallRequest


@tool
def calculate_tip(bill_amount: float, tip_percentage: float = 20.0) -> str:
    """Calculate the tip amount for a bill."""
    tip = bill_amount * (tip_percentage / 100)
    return f"Tip: ${tip:.2f}, Total: ${bill_amount + tip:.2f}"


class DynamicToolMiddleware(AgentMiddleware):
    """Middleware that registers and handles dynamic tools."""

    def wrap_model_call(self, request: ModelRequest, handler):
        # 真实场景里这里可以从 MCP 服务器、数据库加载工具
        updated = request.override(tools=[*request.tools, calculate_tip])
        return handler(updated)

    def wrap_tool_call(self, request: ToolCallRequest, handler):
        # 让智能体知道怎么执行这个「后来才出现」的工具
        if request.tool_call["name"] == "calculate_tip":
            return handler(request.override(tool=calculate_tip))
        return handler(request)


agent = create_agent(
    model="gpt-5.5",
    tools=[get_weather],  # 只有静态工具注册在这里
    middleware=[DynamicToolMiddleware()],
)
```

实测模型确实调用了这个运行时才出现的工具：

```
[ai] 调用 calculate_tip({'bill_amount': 85, 'tip_percentage': 20}) id=call_49ebcbbd...
[tool] 小费 $17.00，合计 $102.00
```

> [!NOTE]
> **`wrap_tool_call` 这个钩子不能省。**
> 少了它，智能体不知道这个新工具该怎么跑——
> 它只见过工具的名字和 schema，没有执行入口。

## 其他工具来源

### 预置工具与工具包

LangChain 提供了大量开箱即用的预置工具和工具包
（网页搜索、代码解释、数据库访问等），
完整清单见官方
[tools and toolkits](https://docs.langchain.com/oss/python/integrations/tools) 页面。

### MCP 服务器

[Model Context Protocol](https://modelcontextprotocol.io) 是 standardized 的工具暴露协议。
`MCPAdapter` 可以把 MCP 服务器的工具转成 LangChain 工具：

```python
from langchain.agents import create_agent
from langchain.mcp import MCPAdapter


async with MCPAdapter("https://example.com/mcp") as adapter:
    tools = await adapter.list_tools()
    agent = create_agent("claude-sonnet-4-6", tools)
```

> [!NOTE]
> `langchain.mcp` 需要 `langchain[mcp]>=1.4.0`，目前是 beta，API 可能变。

### 服务端工具（Server-side tool use）

有些模型自带在服务端执行的工具（网页搜索、代码解释器等），
不需要自己定义或托管逻辑，详见
[tool calling 文档](https://docs.langchain.com/oss/python/langchain/models#server-side-tool-use)。

## 总结

工具这一层的 API 很薄——一个 `@tool` 装饰器就够了。
但要写好用的工具，有几个必须注意的点：

1. **类型注解是必需的，docstring 是模型的唯一线索**。
   描述写清楚，模型才选得对。
2. **工具名用 `snake_case`**，并且避免重名——
   重名不会报错，但模型会随机挑一个。
3. **`config` 和 `runtime` 是保留名**，不能当业务参数用。
4. **`ToolRuntime` 是访问上下文的唯一入口**：
   state 是短期记忆、context 是单次运行的不可变数据、
   store 是跨会话的长期记忆，三者别搞混。
5. **写了 context 就要带泛型**（`ToolRuntime[UserContext]`），
   否则会刷一串 Pydantic serializer 警告。
6. **返回 `Command` 必须自带 `ToolMessage`**，
   `tool_call_id` 从 `runtime.tool_call_id` 拿。
7. **工具异常要用 `wrap_tool_call` 中间件兜住**，
   转成 `ToolMessage` 模型才能自己纠正。
8. **工具不是越多越好**，
   用 `wrap_model_call` 按权限和状态动态过滤。
9. **`return_direct=True` 会跳过后续模型调用**，
   只有在结果不需要再加工时才用；
   并行调用时必须「全部」都是 `return_direct` 才提前结束。
10. **检索类工具要返回完整段落**，
    只返回命中行的话，模型拿到的是个小标题而不是规则本身。
